# 发布后验证

这两份不是 CI 的一部分，是**手动跑的发布后程序**。CI 验的是仓库里的代码，这两份验的是**用户实际拿到的东西**——两者不是同一个问题。

| 脚本 | 什么时候跑 | 它回答什么 |
|---|---|---|
| `verify-from-registry.sh <临时目录> <版本>` | 每次 npm 发布之后，**必跑** | 从 registry 装进隔离前缀，用装出来的二进制跑完主路径 |
| `lifecycle-dogfood.sh <临时目录> <bin.js 路径> <标签> [额外 install 参数]` | 里程碑验收；换 OS / 换 dsh 版本时 | 在真机真 dsh 上跑完整生命周期 |

## 为什么必跑

`verify-from-registry.sh` 是**主检测器，不是安全网**。三轮战绩：

| 版本 | CI | 回装后发现 |
|---|---|---|
| 0.1.0 | 全绿 | **5 个缺陷** |
| 0.2.0 | 全绿 | **1 个缺陷**（`init` 打印的命令复制运行会 exit 0 什么都不做） |
| 0.3.0 | 全绿 | 0 |

前两轮的缺陷没有一个能被 CI 抓到，因为它们全都活在"打包 → 发布 → 安装"这段 CI 不经过的路上。**流水线全绿不等于交付**。

0.3.0 是第一次零发现——这是一个数据点，不是可以停跑的理由。

## 隔离红线

两份脚本都必须遵守，改动时不要破坏：

- 每一条 dsh 相关路径都在传入的临时目录下；**绝不碰用户真实的 `DSH_HOME`**；
- 脚本里不出现 `$HOME` / `$USERPROFILE` / `~`——路径一律由调用方显式传入；
- `rc` 必须紧贴命令捕获。中间插一条 `echo` 就会把 `$?` 冲掉，读出"报错了但 rc=0"这种幻觉（实际踩过三次）。

## 断言写法

正面断言，别只查"没有失败标记"：命令没跑、跑了但什么都没做、以及跑成功了，在"没有错误输出"这个判据下长得一模一样。`verify-from-registry.sh` 的 ⑪ 就是范例——组装成功之后还要**读产出内容**确认赢的是 `prefer` 指定的那个来源，因为两个来源部署到同一路径，只看"文件在"证明不了任何事。
