# ADR-0003：子进程超时由本仓自己兑现，且永不终止进程树

- 状态：Accepted
- 日期：2026-08-19

## 背景

`dshpack` 会 spawn 外部命令：`dsh --version`、`dsh --profile <name>`、`pnpm --version`，
以及 `dsh` 不在 PATH 时的兜底 `npx --yes @deepseek-ai/dsh`。这些调用都带 `timeout` 选项，
看上去是有界的。

它们不是。

`execa` 的 `timeout` 到期只终止**直接子进程**。若该子进程派生了继承 stdio 的**孙进程**，
孙进程在存活期间继续持有 stdout/stderr 管道，而 execa 返回的 promise 要等这些流关闭才
settle。于是被 await 的调用**永不返回**，声明的超时形同虚设。

这条路径在真实用户身上是默认路径，不是边缘情况：

- 用户机器上**没有安装 `dsh`**（对一个刚装上 dshpack 的人来说这是常态）；
- 探测链落到 `npx --yes @deepseek-ai/dsh`，npx 必然派生孙进程去下载并执行该包；
- `dshpack uninstall` / `doctor` / `switch` 因此可以无限挂死。

`uninstall` 尤其严重：它在事务收尾阶段跑 doctor 做装后校验，所以挂死发生在一次**已经在
改用户磁盘**的操作中途。

### 为什么不能"杀干净就完了"

最直觉的修法是让 execa 终止整棵进程树（`killDescendants: true`）。本仓**拒绝**这么做：
execa 在 Windows 上通过 `taskkill /T` 实现进程树终止，而我们无法保证那棵树里只有自己派生的
进程。用户很可能正在另一个终端里跑 `dsh`；误杀用户的进程是比挂死更严重的后果。

「只终止本工具直接派生的子进程」是本仓既有的安全红线，本 ADR 不放宽它。

### 实证

windows-latest 上三条经由 doctor 走到该路径的用例，**给多少预算就消耗多少**：

```text
每用例上限 20s  ->  三条全部耗时 20s
每用例上限 60s  ->  60407ms / 60460ms / 60428ms
```

耗时跟随上限变化是**阻塞**的签名，不是"慢"。同一份代码在开发机上 1951ms / 2252ms 就返回，
因为开发机的 PATH 里有 `dsh`，走的是快路径，从不进入 npx 兜底分支——**这个缺陷在本地
复现不出来**。

## 决策

1. **每一次 spawn 都由本仓自己的看门狗兜底**，不把库的 `timeout` 选项当作唯一保证。
   实现为 `awaitDirectChild(child, timeout)`：把子进程 promise 与一个 `timeout + 250ms`
   的定时器 race。250ms 宽限让 execa 自己的超时有机会先正常 settle，从而在常见情况下
   保留它更丰富的结果。

2. **到期时的行为**：标记 `timedOut`，向**直接子进程**发送 SIGTERM，
   **立即返回已收集到的 stdout/stderr，不等待流关闭**。

3. **`killDescendants` 恒为 `false`。** 孤儿孙进程放它自己退出。宁可留下一个短命的孤儿
   进程，也不误杀用户的 `dsh`。

4. **返回后必须 `unref` 子进程句柄与 stdout/stderr**，否则被继承的管道会让 CLI 在命令
   逻辑早已结束后仍不退出。

5. **成功路径必须 `clearTimeout`**。这条由一条独立测试钉住（断言成功返回后 kill 未被
   调用），因为定时器泄漏是静默的——它不会让任何断言失败，只会让进程晚几百毫秒退出。

6. **看门狗不吞错误**：它把 rejection 转成返回值，所以每个调用点必须显式检查
   `exitCode` / `failure` 并转成本域的错误类型。改造既有调用点时逐个核对，不得依赖
   "原来会抛"这一隐式行为。

## 对贡献者的规则

**看到代码里写着 `timeout:` 不等于这条路径有界。** 要问的是：

> 这个命令会不会派生孙进程？

`npx`、`.cmd` shim、Corepack、以及任何 launcher 包装器——都会。会，就必须走
`awaitDirectChild`。新增 spawn 点时这是 review 的必查项。

**回归测试必须自己合成该形态**，不得依赖"机器上恰好没装 dsh"：一个 launcher 派生
`stdio: 'inherit'` 的后代，后代忽略 SIGTERM 并持有管道若干秒。测试自身必须带**独立
安全阀**（超期主动抛错），不能写成"没修好就挂到套件超时"——纯微任务链会饿死事件循环，
导致挂死而不是超时，runner 的 testTimeout 救不了。

## 后果

**收益**：所有子进程调用真正有界。一个没装 `dsh` 的 Windows 用户不会再看到
`dshpack uninstall` 卡在事务中途。

**代价**：

- 超时路径的 stdout/stderr 可能是**部分的**——我们返回的是超时时刻已收到的片段，
  而不是完整输出。诊断日志因此可能被截断，这是为可终止性付出的自觉代价。
- 超时后可能残留一个孤儿孙进程，直到它自己退出。这是安全红线的直接后果，接受。
- 每次 spawn 多一个定时器。相对于进程创建的开销可以忽略。

**未解决**：`npx --yes @deepseek-ai/dsh` 兜底会在 `uninstall` 的事务收尾校验中发起一次
**联网下载**。它有慢路径提示，是有意设计；但"卸载时联网装包"是否恰当是一个独立的架构
问题，本 ADR 不做裁决，留待单独决定。
